## 🔐 Types of Encryption

### 1. Symmetric Encryption
- Uses a single, shared secret key for both encryption and decryption.  
- It is very fast and efficient, making it ideal for encrypting large amounts of data.

---

### 2. Asymmetric Encryption
- Uses a pair of keys — a **public key** and a **private key**.  
- Data encrypted with the public key can only be decrypted with the private key.  
- It is slower than symmetric encryption but provides **secure key exchange** and **digital signatures**.  
- Commonly used in **TLS/SSL**, **SSH**, and **PGP**.

---

## 🧠 How Asymmetric Encryption Enables Secure Communication

**The server has two keys:**
- **Public key** → shared with anyone (e.g., clients, browsers).  
- **Private key** → kept secret on the server.

**When a client wants to communicate securely:**
1. It retrieves the server’s public key.  
2. It uses that public key to encrypt a **symmetric session key** (a random key generated by the client).  
3. The client sends this encrypted session key to the server.  
4. The server uses its private key to decrypt the session key.  
5. Now both client and server share the same symmetric key, which they use to encrypt and decrypt data efficiently.

➡️ This combination of **asymmetric (for key exchange)** and **symmetric (for data encryption)** methods forms the basis of **TLS/SSL encryption** used in HTTPS.

---

## 🧾 How SSL/TLS Certificates Work with HTTPS

### 1. Certificate Creation

1. The server provides its **public key** and **domain name** to a **Certificate Authority (CA)**.  
2. The CA verifies the domain ownership and issues an **SSL/TLS certificate**.  
3. The certificate contains:
   - The server’s domain name  
   - The server’s public key  
   - The CA’s digital signature (which proves it was issued by a trusted authority)

📘 **Conceptually:**
```
SSL Certificate = Server Public Key + Domain Name + CA Signature
CA Signature = Server Public Key + CA Public Key
```

---

### 2. Verification and Secure Connection Flow

**Server → Client:**  
When a client connects over HTTPS, the server sends its **SSL certificate** and **Server Public Key**.

**Client Verification:**
1. The client checks the **issuer** of the certificate.  
2. It retrieves the **Certificate Authority (CA) Public Key**.  
3. It uses the CA’s public key to verify the **CA’s digital signature**.  
4. If valid, it confirms that the **server’s public key** belongs to the correct domain and has not been tampered with.

**Key Exchange:**
- The client generates a random **session key**.  
- It encrypts this key using the **server’s public key** and sends it to the server.

**Server Decryption:**
- The server decrypts the session key using its **private key**.  
- Both sides now share the same **session key**, allowing secure, encrypted communication to begin.

## ⚙️ Configure HTTPS Secure Connection with NGINX

If you already have an **SSL/TLS certificate**, configure NGINX to serve your site securely using HTTPS:

```nginx
# Redirect HTTP to HTTPS
server {
    listen 80;
    server_name mysite.com www.mysite.com;
    return 301 https://$host$request_uri;
}

# HTTPS server
server {
    listen 443 ssl;
    server_name mysite.com www.mysite.com;

    ssl_certificate /etc/letsencrypt/live/mysite.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/mysite.com/privkey.pem;

    location / {
        proxy_pass http://localhost:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
